# M7 — SPI Flash SSD for the Brevia2 Z80 CP/M (SST25VF020)

> **For Hermes:** Execute this plan task-by-task (TDD, sim-first) using subagent-driven-development. Focus is _planning_ only this turn — no implementation.

**Goal:** Add a persistent 256 KB "solid-state disk" (SST25VF020 SPI flash) to the Brevia2 TV80/Z80 CP/M system as CP/M **drive B:** , giving the machine real power-off-persistent storage.

**Architecture:** An I/O-mapped **SPI byte-engine controller** (parallels the proven RAM-disk peripheral at I/O 0x20/0x21/0x22) that the Z80 drives at the **byte** level (the controller clocks the physical SPI bits at ≤20 MHz). The CBIOS implements the full SST25VF020 command set on top of that byte engine, and dispatches CP/M disk ops for drive B: to a flash driver; drive A: stays on the existing RAM disk. Flash writes use **erase-before-write** (programming only clears 1→0; setting a bit back to 1 requires a 4 KB sector erase).

**Tech stack:** Verilog-2001 RTL (25 MHz Z80/TV80 core, already working), Synplify + Diamond 3.14, iverilog + Questa sim, the macro-assembler AS (cpm/asw) for the CBIOS, GWMON-80 monitor for board load.

---

## Context & assumptions (verified)

- **Chip:** `SST25VF020-20-4C-SAE`. 2 Mbit = **256 KB** SPI serial flash. Max SPI clock **20 MHz** (the "-20" suffix). It is a **user** flash on the Brevia2, entirely separate from the FPGA's internal bitstream config flash.
- **Pins (from the demo SoC `project/demo_latticexp2_brevia_soc.lpf`, verified):**
  - `spi_csn` = **11**, `spi_miso` = **16**, `spi_mosi` = **15**, `spi_sclk` = **13**.
  - Our `build/brevia2.lpf` does **not** yet assign these pins — must be added.
- **Geometry:** 256 KB total; addressable as A17–A0 (A23–A18 are don't-care). **4 KB sectors** (erase unit, 64 of them), **32 KB blocks** (8, erase 0x52), 256-byte pages (for AAI streaming), 1-byte granular program.
- **Command set (Microchip DS20005078, verified):**

  | Command | Opcode | Notes |
  |---|---|---|
  | Read | `03H` | 3 address bytes, continuous output until CS# high |
  | Byte Program | `02H` | 1 data byte per WREN |
  | AAI Program (stream) | `AFH` | WREN + opcode + addr + continuous bytes; must not cross a 256-byte page without re-issuing |
  | Sector Erase (4 KB) | `20H` | addr[AMS..A12]; self-timed; poll BUSY |
  | Block Erase (32 KB) | `52H` | self-timed |
  | Chip Erase | `60H` (or `C7H`) | self-timed |
  | RDSR | `05H` | bit0 = WIP/BUSY; poll after erase/program |
  | WREN | `06H` | required before every program/erase |
  | WRDI | `04H` | ends AAI mode |
  | JEDEC ID | `9FH` | returns manufacturer **`BF`** (SST/Microchip) + device id — **use this to verify the chip on silicon** |
  | RDID | `90H`/`ABH` | legacy |

- **Erase-before-write is mandatory:** flash cells only go 1→0 on program; a 0→1 transition requires erasing the whole 4 KB sector (to all 0xFF) first. Empty/never-written 0xFF regions can be programmed directly.
- **Existing system (all working):** RAM disk = drive A: (I/O 0x20/0x21/0x22, bank-B auto-increment), UART console = I/O 0x80/0x81, `boot_done` = OUT 0x30,1, CP/M 2.2 (CCP=0xE400, BDOS=0xEC00, CBIOS=0xFA00-0xFBF2), GWMON-80 monitor. 25 MHz PLL, combinational reset.
- **Persistent vs. volatile (the point of M7):** the RAM disk (A:) is volatile and rebuilt each cold boot; the flash (B:) survives power-off — this is the real win.

## Proposed I/O port map (byte-engine controller; final addresses locked during Task 2)

Avoid conflicts with existing ports (0x20-0x22 RAM disk, 0x30 boot_done, 0x80-0x81 UART). Proposed:

| Port | Dir | Function |
|---|---|---|
| `0x40` | r/w | SPI_DATA — read = clock in 1 byte from flash; write = clock out 1 byte to flash |
| `0x41` | w | SPI_CTL — bit0 = CS# (write 0 = assert low, write 1 = release high) |
| `0x42` | r | SPI_STAT — bit0 = transfer-busy, bit1 = flash WIP (from RDSR is also fine) |

The controller clocks each byte transfer at **12.5 MHz** (25 MHz / 2, safely under the 20 MHz flash max) with MSB-first framing, while CS# is asserted. The CBIOS owns the protocol framing (which opcode, how many address bytes, where to end CS#).

**Verify:** `grep -niE 'spi_(csn|miso|mosi|sclk)' build/brevia2.lpf` shows the 4 lines; run the Diamond build (`build/*.tcl`) and confirm no pin-unplaced errors. Commit.

### Task 2 — Write the SPI flash controller RTL (`rtl/spi_flash.v`)

**Objective:** an I/O-mapped byte engine: 8-bit parallel<->SPI serial with CS control, clocked at 12.5 MHz.
**Files:**
- Create: `rtl/spi_flash.v`
- Create: `tb/tb_spi_flash.v`
- (Sim model for the flash itself, or reuse an SPI-flash model)

**Interface sketch (`-g2001` clean):**
```verilog
module spi_flash (
  input  clk, rst,
  input  cs,        // CS# control from the CPU (via 0x41 bit0), active-low semantic
  input  wr, rd,    // one-shot strobe from the I/O decode for 0x40
  input  [7:0] din, // byte to send (write)
  output [7:0] dout,// byte received (read)
  output spi_sclk, spi_csn, spi_mosi,
  input  spi_miso
);
```
- A 4-bit counter generates the 12.5 MHz shifted SCK (SCK toggles every 2 clk). MSB-first. While `cs` asserted, every 0x40 access shifts 8 bits.
- **Pitfalls (banked):** SCK must idle low (CPOL=0, CPHA=0); drive SCK/MOSI only when CS# is low; never assert CS# and SCK from unrelated flops (clock the whole thing off `clk`); MISO sampled on the rising edge of the generated SCK.

**Task 2a:** Write `tb/tb_spi_flash.v` asserting CS, writing a known byte, and verifying the serial waveform and the received byte. **Task 2b:** run iverilog (`source ./env.sh; $IVERO/iverilog -g2001 ...`), confirm pass. Commit.

**Files:**

**Verify:** assemble with 0 errors; a small GWMON-uploadable test (or extend `flashtest.s`) that reads the JEDEC ID and reports `BF`. Commit.

### Task 6 — Add CP/M drive B: to the CBIOS (flash as the disk) + erase-before-write

**Objective:** SELDSK/SETTRK/SETSEC/READ/WRITE dispatch on the drive letter (A: = RAM disk, B: = flash). Add a DPB for the 256 KB drive.
**Files:**
- Modify: `cpm/cbios.asm` — add a `DPB_B` (SPT/blocks sized for 256 KB; note block size and DRM so it's a valid CP/M disk), a DPH_B, and route READ/WRITE for drive B: through the flash driver. Add the drive-number check early in SETTRK/SETSEC/READ/WRITE (like the existing RAM-disk path).
- **Erase-before-write:** use a **4 KB sector buffer in RAM** (e.g., 0x0F00-0x1EFF, clear of the CCP/BDOS/CBIOS/TPA). On a CP/M sector write to B:: load the target 4 KB flash sector into the buffer (if not cached), apply the 128-byte change, then on flush (or when switching to a different 4 KB sector) do: READ the 4 KB → modify → *sector erase* → AAI-program it back. Keep a "dirty" flag so untouched sectors are never erased.
- Note CP/M always calls SECTRAN (XLT=0 → identity) and HOME; ensure drive B: path handles these.

**Verify:** sim boots to `A>`; then in the sim, `B:` + `DIR` works and `SAVE xx B:FILE.COM`/`DIR B:` round-trips without a crash. Commit.

## Risks, tradeoffs & open questions

- **Erase-before-write latency:** each 4 KB sector erase is ~ms; the sector-buffer/write-cache keeps erases rare but a full rewrite of a hot directory sector will be slow. Acceptable for a CP/M data disk (non-critical I/O).
- **Byte engine vs. full hardware controller:** the byte engine is a deliberate middle ground — the CBIOS owns protocol framing (simpler to get right) while the controller does the bit clocking (fast enough at 12.5 MHz). A full opcode-aware controller is a later optimization (M7b) if needed; YAGNI now.
- **AAI page-boundary rule:** AAI (0xAF) cannot cross a 256-byte page without re-issuing; the CBIOS driver must chunk programs at 256 bytes. (Or use per-byte `02` if simpler — slower but always safe.)
- **Drive B: DPB sizing:** the exact SPT/block size/DRM for a 256 KB drive must be chosen so CP/M accepts it (DSM must fit in the 16-bit field; block size 1 KB or 2 KB). Verify DPB byte-alignment so the BDOS copies it correctly (same alignment discipline as the existing drive A: DPB).
- **Open question:** should the flash eventually replace the RAM disk as the *system* (drive A:) boot device for full persistence of the OS too? Not in M7 scope — M7 makes the flash **drive B: (data)**, keeping the fast RAM disk as the boot device. Consider as a follow-up.
- **Open question:** pin 11 also carries something else on some boards? The demo `.lpf` uses it strictly for `spi_csn`; if the board marries it to the config flash's chip-select, the demo's behavior (it already boots and the user-flash demo works on these pins) is our precedent — no conflict expected.
